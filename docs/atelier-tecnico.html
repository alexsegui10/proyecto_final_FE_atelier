01 · Introducción

¿Qué es Atelier?

Atelier es una plataforma web que genera aplicaciones web completas a partir de una descripción en lenguaje natural. El usuario describe lo que quiere construir en un chat; el sistema orquesta 21 agentes de inteligencia artificial que trabajan en cadena y producen un proyecto Next.js funcional con base de datos, autenticación, API, componentes, tests y configuración de despliegue.

Qué genera exactamente: un proyecto Next.js (App Router) con TypeScript, Prisma + PostgreSQL, autenticación con Better Auth, componentes shadcn/ui adaptados al diseño generado, API REST con rutas de Next.js, tests Vitest y Playwright, y scripts de arranque multiplataforma. Todo listo para ejecutar con pnpm demo:setup.

Ejemplo real validado: a partir de la descripción "app de clases de yoga con administrador, profesores y alumnos, reservas y pagos", Atelier genera un proyecto completo en aproximadamente 15 minutos: 14 entidades de dominio, 18 pantallas, sistema de roles RBAC, integración de pagos, seeds con datos realistas y una suite de tests E2E.

02 · Arquitectura del proyecto

Cómo está organizado el código

03 · El sistema agentico por dentro

Cómo está construido cada agente

Cada agente en Atelier no es una clase ni un objeto — es la combinación de tres piezas independientes que el runner une en tiempo de ejecución:

1. System prompt (.md)
Un fichero Markdown en prompts-v3/. Define el rol del agente, qué inputs lee (qué ficheros del .atelier/ anterior), qué output debe producir, y las reglas que debe respetar (R0, R1… Rn). Es el "contrato de comportamiento".
2. Schema Zod (.schema.ts)
Un schema TypeScript en contracts-v3/ que describe exactamente el JSON que debe producir el agente. Incluye refinements con invariantes de negocio. Si el output no pasa el z.parse(), se emite una violación.
3. Config en el runner
Una entrada en AGENT_CONFIG_V3 con el timeout, el sentinel de parada, y el nombre del fichero artifact que debe producir. El runner usa esto para saber cuánto esperar y cuándo considerar el agente terminado.

Cómo se invoca un agente

El runner (runner-generator-v3.ts) lanza un subproceso de claude.exe con el system prompt del agente y el contexto acumulado (los artefactos de las waves anteriores). Lee el stdout por streaming hasta detectar el sentinel de parada, luego parsea el JSON y lo valida con el schema Zod. 

// runner-generator-v3.ts — simplificado
async function runGeneratorAgentV3(input: AgentRunInputV3) {
  // 1. Carga el system prompt del agente
  const prompt = await readFile(`prompts-v3/${input.agent}.md`);

  // 2. Lanza Claude como subproceso
  const child = spawn("claude", ["--system", prompt, "--output-format", "json"]);

  // 3. Lee el output por streaming hasta el sentinel
  const rawJson = await collectOutput(child, config.stopSentinel);

  // 4. Valida con el schema Zod del agente
  const artifact = getSchemaForAgent(input.agent).parse(rawJson);

  // 5. Escribe los ficheros físicos en el workDir
  await writeArtifactFiles(artifact, input.workDir);

  return { artifact, filesCreated, summary };
}

Ejemplo real: el agente Bootstrap

Su system prompt (prompts-v3/bootstrap-devops.md) le ordena ser la autoridad única sobre variables de entorno. Ningún otro agente puede declarar un process.env.X sin que esté registrado en el envManifest de Bootstrap — si lo hace, el QA Reviewer emite una violación BLOCKER.

Su schema Zod (contracts-v3/bootstrap.schema.ts) valida:

export const bootstrapOutputSchema = z.object({
  envManifest: z.array(z.object({
    key:      z.string(),           // nombre de la variable
    required: z.boolean(),
    source:   z.enum(['env', 'generated', 'default']),
    example:  z.string(),
  })),
  dockerServices:  z.array(...),
  healthcheckUrl:  z.string().url(),
  filesProduced:   z.array(z.string()),
}).refine(
  (d) => d.envManifest.every(e => e.source !== 'hardcoded'),
  "R0 — ninguna variable puede estar hardcodeada en el código"
);

Por qué Zod y no solo TypeScript: TypeScript solo existe en tiempo de compilación. Los agentes producen JSON en tiempo de ejecución — puede tener campos que faltan, tipos incorrectos o invariantes rotas. Zod valida el JSON real, no los tipos, y permite expresar reglas de negocio como refinements ("el source nunca puede ser 'hardcoded'").

04 · Las 7 waves de generación

Qué hace cada agente

Los 21 agentes están organizados en waves por dependencias: un agente de la wave N solo puede ejecutarse cuando todos los agentes de los que depende han terminado. Los agentes de una misma wave que no dependen entre sí se ejecutan en paralelo con Promise.allSettled.

Wave 1A
Bootstrap
bootstrap-devops Lee el PRD y genera toda la infraestructura de arranque: .env.example, docker-compose.yml, scripts de setup cross-platform y el validador de entorno. Es la autoridad única sobre variables de entorno — ningún otro agente puede declarar variables sin registrarlas aquí.
Wave 1B
Arquitectura
architect Lee el PRD y el output de bootstrap. Decide la estructura completa de la aplicación: qué páginas existen, qué entidades del dominio hay, qué roles de usuario, cómo se llaman las rutas, qué módulos tiene el proyecto. Su output es el contrato maestro que leen todos los agentes posteriores.
Wave 2A
Diseño visual
PARALELO
ux-ui-designer Define el design system base: tokens de color, tipografía, espaciado y el "design vibe" general de la app. Usa el Stitch SDK de Google para generar mockups de las pantallas principales.
layout-architect Diseña la estructura visual de cada página: qué secciones tiene, qué componentes van en cada una, cómo se compone el layout. Produce el layout-tree.json que es la referencia estructural para visual-adapter.
brand-identity Define los tokens de marca específicos del proyecto generado: paleta de color exacta con referencias hex, escala tipográfica, microcopy (textos de botones, placeholders, mensajes de error en el idioma de la app).
Wave 2B
Dominio
PARALELO
domain-modeler Lee el output del architect y define el modelo de dominio completo: todas las entidades, sus campos, tipos y relaciones. Este modelo se convierte en el schema Prisma del proyecto generado.
persistence Traduce el modelo de dominio a un schema.prisma concreto con relaciones, índices, constraints y configuración del adaptador de base de datos.
seeds-shape Define la forma de los datos de ejemplo que se cargarán en la base de datos. No genera los datos todavía — define su estructura para que el agente seeds-fixtures los genere correctamente en la wave 5.
Wave 3
Seguridad
PARALELO
service-layer Genera la capa de servicios: las funciones de lógica de negocio que intermedian entre la API y la base de datos. Aquí viven las reglas como "un alumno no puede cancelar una clase de otro alumno".
auth-security Configura el sistema de autenticación con Better Auth: registro, login, sesiones, tokens, cookies HttpOnly. Genera los ficheros de configuración y los middlewares.
rbac-authorization Define y aplica el sistema de permisos por rol (RBAC). Genera las políticas de acceso: qué puede hacer cada rol en cada ruta y qué datos puede ver.
Wave 4
Frontend completo
api-backend Genera todas las rutas de API (Next.js Route Handlers): los endpoints REST con validación de entrada (Zod), llamadas a la service-layer y respuestas tipadas.
frontend-architect Define cómo se organiza el código React: hooks, providers de contexto, estructura de carpetas del cliente. El contrato que siguen ui-components y forms-validations.
ui-components Genera el catálogo de componentes React de la app: tablas, cards, modales, navegación. Usa shadcn/ui como base y aplica los tokens de brand-identity.
forms-validations Genera los formularios de la app con React Hook Form + Zod: todos los campos, sus validaciones, mensajes de error y comportamiento de envío.
visual-adapter El agente más complejo de wave 4. Lee los HTMLs generados por Stitch (los mockups visuales) y los convierte en páginas JSX reales: inyecta test-ids, conecta los datos de la API, aplica el microcopy de brand-identity y preserva el diseño visual.
Wave 5 + 6
Datos y QA
seeds-fixtures Genera los datos de ejemplo realistas para la base de datos: usuarios, contenido, relaciones. Usa la shape definida en wave 2B y los nombres del dominio concreto de la app.
tests-writer Genera la suite de tests: unitarios con Vitest para la service-layer y E2E con Playwright para los flujos principales de usuario (registro, login, CRUD).
qa-reviewer Revisa todos los artefactos producidos buscando inconsistencias: variables de entorno sin registrar, rutas sin protección de rol, componentes sin test-ids. Emite violaciones con severidad warn / error / critical.
Wave 7
Visual QA
visual-qa Arranca la aplicación generada con Playwright headless. Ejecuta flujos reales de cliente y administrador: registro, login, CRUD, navegación entre páginas. Captura screenshots, detecta errores de consola en runtime y errores visuales con comparación de pixels (pixelmatch). Si detecta fallos, los enruta al agente responsable para que los corrija.
05 · Calidad y robustez

El fix loop: cómo se corrigen los errores

El sistema no asume que los agentes producen output perfecto a la primera. Después de cada wave, el qa-reviewer analiza los artefactos producidos. Si encuentra violaciones, el orquestador no pasa a la siguiente wave — manda los errores de vuelta al agente responsable usando el violations-router-v3.ts.

Agente produce artefacto
→
z.parse() valida el JSON
↓ si pasa ↘ si falla → violación inmediata
qa-reviewer analiza la wave
→
¿hay violaciones?
NO →
siguiente wave
SÍ (hasta 3 rondas) →
violations-router: ¿qué agente lo causó?
↓
Agente responsable recibe el error y regenera
→
z.parse() de nuevo

Las violaciones tienen tres niveles de severidad:

SeveridadQué significaQué hace el orquestador
warn Algo mejorable pero no bloqueante Acumula en el informe final, no interrumpe
error Fallo recuperable: el agente puede corregirlo Lanza el fix loop (máximo 3 rondas)
critical Fallo irrecuperable: el agente tiene un bug de diseño Detiene la generación inmediatamente, reporta al usuario
06 · Persistencia

La base de datos de la plataforma

Atelier tiene su propia base de datos PostgreSQL (distinta de la que genera para el usuario). Almacena usuarios, proyectos, generaciones y todos los eventos del orquestador para que el usuario pueda retomar generaciones y ver el historial. 

// prisma/schema.prisma — base de datos de Atelier

model User       { id String  @id  // id de Clerk }
model Project    { id String; prd Json; generations Generation[] }
model Generation { id String; status String; agentRuns AgentRun[]; events Event[] }
model AgentRun   { agent String; status String; output Json }
model Event      { type String; payload Json  // wave.started, agent.completed... }

El campo Event.type es un String libre — no un enum. Esto permite añadir nuevos tipos de evento sin migraciones de base de datos. El payload se guarda como Json y el frontend lo interpreta según el type.

08 · Decisiones de diseño

Por qué se tomaron estas decisiones

Subproceso en vez de API HTTP
Los agentes se invocan lanzando claude.exe como subproceso en lugar de llamar a la Anthropic API directamente. Razón: el CLI de Claude maneja el contexto, el streaming y los reintentos de forma nativa, y permite usar los mismos prompts que un desarrollador usaría manualmente.
Un .md por agente, no código
Los system prompts son ficheros Markdown editables, no strings en el código TypeScript. Esto permite iterar sobre el comportamiento de un agente sin tocar el código del orquestador, y hace que los prompts sean revisables con diff de git como cualquier otro fichero.
Artefactos JSON + Zod, no texto libre
Cada agente produce JSON estructurado, no texto libre. Esto hace el output verificable programáticamente, trazable (se guarda en BD), y consumible por el siguiente agente de forma determinista. El texto libre solo aparece en el campo summary para mostrar al usuario.
Skeleton como plantilla base
Los agentes no generan un proyecto desde cero — escriben sobre una plantilla base (lib/skeleton/) que ya tiene configurado Next.js, TypeScript, ESLint y Prisma. Los agentes rellenan el contenido específico del dominio. Esto reduce errores de configuración y hace el output más predecible.
SSE para el Studio
El Studio muestra el progreso en tiempo real usando Server-Sent Events (SSE) en lugar de WebSockets. Razón: los eventos de generación son unidireccionales (servidor → cliente), SSE es más simple de implementar con Next.js Route Handlers y no requiere infraestructura adicional.
Waves paralelas con Promise.allSettled
Dentro de una wave, los agentes sin dependencias entre sí se ejecutan en paralelo. Se usa Promise.allSettled en lugar de Promise.all para que el fallo de un agente no cancele los demás — el orquestador recoge todos los resultados y decide si continuar o activar el fix loop.
